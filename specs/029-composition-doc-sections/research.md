# Phase 0 Research: Structured Feature Documentation in Feature Composition

All four scope decisions were resolved with the user before planning (see spec `## Clarifications`). This file records the codebase-grounded design decisions, with file:line evidence, and the Framework-First reuse map.

## R1 — Reuse the composition AI prompt/ingest; add a pure section canon

- **Decision**: keep `buildCompositionPrompt` / `parseCompositionIngest` (`PoTool/ai/compositionAiAssist.ts`) and the `CompositionProposal { summary, description, acceptanceCriteria, fields, rationale }` contract; add a new pure module `featureDocSections.ts` that owns the nine-section structure and normalizes/validates the `description` string on ingest.
- **Rationale**: the shipped 017 pattern (prompt out → strict JSON → editable draft, propose-only) already fits; the only genuinely new logic is *structuring and validating the description*, which has no home today. `normalizeRichTextToPlainText` (`utils/richTextPlainText.ts`) flattens markup but has no concept of sections.
- **Alternatives**: force structure purely via the prompt with no ingest normalization (rejected — a model that drops/reorders a section would produce an inconsistent document; FR-004 requires guaranteed completeness); a rich ADF/section model (rejected — the instance stores descriptions as plain text, `FeatureCompositionTab.tsx:241`).

## R2 — The nine sections, order, and validation markers

- **Decision**: the canonical order is exactly the spec's list — Description, Benefit Hypothesis, Acceptance Criteria, Assumptions, Dependencies, In Scope, Out of Scope, Risks, Non-Functional Requirements (NFR) — as named constants. `normalizeFeatureDescription(raw)` parses the model's description by these labels, re-emits all nine in order, and inserts a **validation-flagged placeholder** for any missing section. Markers are three fixed strings: `⚠ REQUIRES BUSINESS VALIDATION`, `⚠ REQUIRES TECHNICAL VALIDATION`, `⚠ REQUIRES BUSINESS & TECHNICAL VALIDATION`.
- **Rationale**: FR-001/FR-004/FR-020. Named constants keep the order/labels/markers out of magic strings and make the tests assert against one source of truth.
- **Default marker-kind mapping** (the AI chooses, but the placeholder inserter needs a default): Benefit Hypothesis / In Scope / Out of Scope / Risks → **Business**; Dependencies / NFR → **Technical**; Description / Acceptance Criteria / Assumptions → **Business & Technical**. The PO can edit before committing.
- **Section rendering**: labels are emitted as plain-text headings (e.g. `Description:` on its own line) consistent with how the instance stores/round-trips descriptions; the exact markup is not load-bearing to the requirement (labeled sections, in order).

## R3 — No AI self-attribution (hard output rule)

- **Decision**: `stripAiAttribution(text)` removes any sentence/phrase attributing authorship to AI ("generated by", "drafted by AI", "as an AI", "AI-composed", etc.) as a defensive net, and the prompt explicitly forbids it. Applied in `parseCompositionIngest` before the proposal reaches the draft.
- **Rationale**: FR-003/SC-004. Belt-and-suspenders: instruct the model *and* strip on ingest, so a stray phrase never reaches Jira. The validation markers are framed as "missing information," never as an AI disclaimer (FR-022).
- **Alternatives**: prompt-only (rejected — no guarantee); rejecting the whole reply on any match (rejected — too brittle; stripping the phrase preserves the useful content).

## R4 — Acceptance criteria in both places (already half-built)

- **Decision**: AC continues to be written to the dedicated AC field — `FeatureCompositionTab.tsx` already discovers `acceptanceCriteriaFieldId` (`:92`) and writes it on commit (`:287`, via `saveField`) — and additionally appears as the full text of the description's "Acceptance Criteria" section (the normalizer keeps it there).
- **Rationale**: FR-010. The AC-field write is existing behavior; the only change is ensuring the same AC text is present in the description section too (the normalizer does not strip it).
- **Alternatives**: AC only in the field with a pointer in the description (rejected per clarification 1 — the user wants the full AC in both).

## R5 — Risk linking via `createIssueLink`, keys from the Risks section

- **Decision**: `extractRiskLinkKeys(description)` pulls Jira issue keys (`/[A-Z][A-Z0-9]+-\d+/`) from the **Risks section** of the final (possibly PO-edited) description. On commit, after the Feature exists, create a `Relates` link (`createIssueLink({ type:{name:'Relates'}, inwardIssue:{key: featureKey}, outwardIssue:{key: riskKey} })`) per extracted key. Failures are non-fatal and surfaced.
- **Rationale**: FR-030/031/032/033. Extracting at commit (not from the raw AI reply) respects PO edits and needs no new draft field. `createIssueLink` (`jiraApi.ts:256`) already exists and is documented as non-fatal-by-contract — a perfect fit. Keys come only from the material's text (surfaced in the Risks section), so the tool never searches Jira (FR-033).
- **Link type name**: `Relates` is Jira's default "relates to" link type; if an instance renames it, the type name is the one configurable point (default `Relates`).
- **Alternatives**: thread `riskLinkKeys` from the AI reply through the draft (rejected — brittle across PO edits); search Jira for risk tickets (rejected per clarification 2).

## R6 — Commit wiring (create + update)

- **Decision**: `buildCompositionCommit` computes `riskLinkKeys` from `draft.description`; `runCompositionCommit(diff, { createIssue, saveField, createIssueLink })` creates the links after the create/update using the resulting Feature key (`outcome.createdKeysByLocalId.feature` for new, `draft.existingIssueKey` for update). Non-fatal: link results are collected into the outcome and shown, never blocking.
- **Rationale**: FR-041/FR-042. Keeps the write orchestration in the existing pure-diff + injected-I/O commit path (testable with a mocked `createIssueLink`), and the update path already shows the proposed description in the draft for review before commit (no silent overwrite).

## Summary of new vs reused

| Concern | Source |
|---------|--------|
| Prompt/ingest contract, editable draft, propose-only, AI gate | **REUSE** `compositionAiAssist.ts` + `FeatureCompositionTab.tsx` |
| AC-field discovery + write, description write, create/update commit | **REUSE** existing composition commit path |
| Issue linking ("relates to"), non-fatal | **REUSE** `createIssueLink` |
| Nine-section normalize/order/flag-placeholders | **NEW** `featureDocSections.ts` |
| Strip AI self-attribution | **NEW** `featureDocSections.ts` |
| Extract risk-link keys from the Risks section | **NEW** `featureDocSections.ts` |
| Prompt guidance (sections, markers, no-AI, risk keys); ingest normalization; commit link step | **MODIFY** existing files |
